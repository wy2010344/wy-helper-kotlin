# 00 - 设计哲学：信号框架的原则

> 本文是全仓库的顶层设计约束。各模块文档（[01 快速上手](01-快速上手.md) / [06 事件与焦点](06-事件与焦点.md) / [03 文字](03-文字.md)）讲"怎么用"，本文讲"为什么这样设计、怎么判断自己有没有写错"。
>
> 典型范例：文本选择系统的纯派生重构（见 [06 跨组件文本选择](06-事件与焦点.md)）——从"命令式 setSelection 同步"迁移为"零命令入口的派生链"，本文所有原则在该案例中均有正反对照。

## 一、核心公理：单向数据流

**Signal 是数据流的起点，不是中间站。**

整个系统是一棵以顶层信号为根、派生计算为枝、绘制为叶的单向树：

```
顶层信号（事实） ──→ memo 派生（计算） ──→ 绘制 / 行为
     ↑ 只允许在这里写                ↑ 这里只许读
```

判断一切问题的总原则：**这段代码是在记录新发生的事实，还是在计算已知事实的结果？**

- 记录事实 → 写信号（合法）；
- 计算结果 → 普通函数或 memo（无副作用）；
- 把计算结果再写回信号 → 几乎总是错的（见下）。

## 二、Signal 的写入边界

只有三类东西允许 set 信号：

1. **用户触发的直接信息**：指针按下/移动/释放（`pointerSelect`、`moveHitTest`）、按键、焦点迁移；
2. **异步世界的回报**：网络返回、定时器回调、平台事件上报；
3. **业务意图的声明**：业务代码说"选中这一段"（`SelectionManager.select`）、"文本变了"（`text = ...`）。

### 合法写入与非法写入的分界

| | 性质 | 例子 |
|---|---|---|
| ✅ 合法 | 新的初始原因进入数据流 | 引擎记录按下快照；业务声明式设置选区 |
| ❌ 非法 | 读派生结果再写回（反向同步） | 键盘扩选后调 `setSelection` 推送给协调者 |

> 历史教训：旧版选区系统中，编辑器每次键盘扩选都要手动调 `SelectionManager.setSelection` 同步全局会话——共 6 处反向同步。重构后这些调用全部删除，行为完全不变，因为信息本来就能沿数据流（本地光标信号 → 派生链）到达目的地。

**判别式：如果删掉这条 set，信息仍能沿数据流自动到达目的地，它就是多余的。**

## 三、派生规则

1. **单一真相源**：任何问题（"谁被选中了"）只有一个权威存储，其余全是它的函数。节点读 `rangeOf` 绘制高亮，不保存任何本地副本。
2. **派生链自带优先级，不用命令失效**：多个来源竞争同一状态时，写成优先级表达式（如 `currentPair` 的推导链：按住中的指针会话 > 编辑器光标 > 定格会话 > 程序化会话）。高优先级出现即自然遮蔽低者——**让位是数据流的性质，不是某段代码执行的效果**。
3. **命令 = 写信号，不是改一堆状态**：Ctrl+A 全选不是"遍历清场再标记"，而是向 `programmatic` 槽物化一条记录，让它参与派生竞争。
4. **惰性物化代替持续同步**：两个真相源需要衔接时（如全局选区 → 编辑器本地光标），用一次性吸收——仅在目标未初始化时以全局值为初值（`absorbGlobalSelection`），此后各自独立流动。这是"零同步"与"交互连续性"之间的正确折衷；不写下来，后人容易重新发明出双向绑定。

## 四、信号的原子性

**同一境遇 = 一个信号 = 一次 set。**

- `PointerSelect(press, release)` 是一条信号，而非 `pressed: Bool` + `anchor` + `releasePos` 三条——按下与松手是同一会话的两态，拆开就会出现"半更新"的非法中间态（历史上 `pressed` 曾是独立信号，导致"松手瞬间 pressed 已空但会话尚未定格"的时序缝隙）。
- 相关属性随载体走：设备类型收进 `HitestResult.device`，而不是平行于命中链的 `lastPointerDevice`（否则两者可能不一致）。

## 五、memo 的使用时机

默认直接计算，满足其一才包 memo：

1. **大负担计算**：注册表排序、全文聚合等明显开销；
2. **返回值需要址稳定**：如 `ranges` 返回同一个 LinkedHashMap——若每次新建对象，下游所有依赖它的 memo 都会判定"变了"而连锁重算。

memo 不是缓存装饰品，是**切断连锁失效的手段**。滥用它会让依赖图变得难以推理。

## 六、职责下放

- **协调者只管协调**：`SelectionManager` 不认识具体节点类型，能力由接口下放（`Selectable.positionForPoint / textInRange / wordRangeAt` 由节点自己实现）；
- **组件自治**：编辑器的光标是编辑器的私事，协调者从不写它，只在派生时读取（`cursorSelPair`）；
- **行为继承、外观组合**：交互内置于基类（`ButtonBase` 的 hover/pressed/focus/disabled），样式层自由覆写而不触碰交互逻辑。

## 七、副作用的受控出口

派生必须无副作用，但系统终究要和外界交互（设光标、同步 IME、请求重绘）。副作用只允许从以下三个受控出口离开数据流：

| 出口 | 性质 | 语义 |
|---|---|---|
| `TrackSignal<T>` | 值驱动的**持续**副作用 | get() 内做计算并追踪依赖；值变化才触发 set() 推给平台（如 `cursorTrack` 设系统光标、`overlayTrack` 定位输入框）；set 可返回清理函数，dispose 时回收 |
| `addEffect(level)` | 批次末尾的**响应式**效果 | 依赖信号批次提交后执行；level 分层保证顺序；effect 执行期间新注册的效果自动排到下一批，杜绝自续期死循环 |
| `addPostRenderEffect` | 帧边界后的**一次性**效果 | 入队后由 `Renderer.render` 每帧 drain 统一消费（如焦点同步到平台）——把"现在立刻做"推迟到安全时点，保证绘制过程是纯计算 |

共同纪律：

1. 副作用只能在这三种形态里发生，禁止在事件处理/绘制中途随手调平台 API；
2. TrackSignal 的 set 以值为准（去重），不是"每次重算都执行"；
3. 需要副作用却拿不到时机时，答案是"排队到正确的阶段"，而不是"现在偷偷做"。

## 八、检验清单（Review 时自问）

1. 这个 set 记录的是事实/意图，还是把计算结果写回去？
2. 删掉这个同步调用，信息还能不能自己流过去？
3. 这几个信号是不是同一件事被拆开了？能否合成一次 set？
4. 这个计算有没有被两处各算一遍？真相存在几份？
5. 出现了"让 A 失效"这类语句吗？——应改成"B 出现时 A 自然让位"。
6. 这段副作用走了三个受控出口之一吗？还是藏在事件/绘制路径里？
